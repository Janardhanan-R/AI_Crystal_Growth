# Assumptions and Limitations

This document states every assumption made in the synthetic-data-generation workflow
(`synthetic/`) plainly, per the project's explicit requirement to prioritize honest reporting
over dataset size or accuracy. Nothing here is intended to be discovered later as an
unstated caveat.

## What the synthetic data is, and is not

- **Is**: a statistical interpolant of the 96-row CrysMAS simulation sample in `data/Table.csv`,
  produced by a `GaussianProcessRegressor` fit on 67 of those rows (the original-train split),
  sampling new `T1..T5` combinations within the observed ranges and predicting `Lc`/`Le` (with
  `D`, `P` derived algebraically) plus noise drawn from the GP's own predictive uncertainty.
- **Is not**: new CrysMAS finite-volume simulation output. No CrysMAS run (or any other
  physics solver) was executed to produce any synthetic row. It is not experimental data. It
  is not validated against any furnace measurement. Every synthetic row carries
  `source = "synthetic_gpr_generated"` so this cannot be confused with original data
  downstream.

## Core assumption: the GP interpolant is a reasonable stand-in for the CrysMAS response surface

This is the load-bearing assumption of the entire generation approach. It is reasonable
*within* the observed T1–T5 ranges, because: (1) `Lc`/`Le` are known from this project's own
prior, independently-validated cross-validation (`src/surrogate.py`, `FastSurrogate`) to be
well-fit by exactly this GPR architecture (CV R² ≈0.977–0.994); (2) the underlying physical
process (steady-state conduction/radiation heat transfer determining an interface position) is
smooth, which is the regime GPs with an RBF kernel are designed for. It is **not** validated,
and not claimed to be valid, outside the observed T1–T5 ranges — no extrapolation is performed
(inputs are sampled only within the training range, and the generator adds a plausibility
guard that discards predictions far outside the observed output range).

## Assumptions specific to `D`

- `D` is **not** generated by an independent model. An earlier version of this pipeline did
  fit a separate GPR for `D` directly and found that its predictions broke the exact
  `D = Lc − Le` identity that holds in 100% of the original data, by amounts comparable to
  `D`'s entire observed range — an unacceptable, physically-inconsistent artifact. The final
  pipeline instead derives `D` algebraically from generated `Lc`/`Le`, exactly as the original
  data does.
- `D`'s uncertainty (`D_gp_std`) is a **propagated, independence-assumption estimate**
  (`sqrt(Lc_gp_std² + Le_gp_std²)`), not a directly fit quantity. This assumption is stated as
  conservative in one specific, checkable direction: the real `Lc`/`Le` are highly collinear
  (Pearson r = 0.992 in the original data), so their true joint prediction error is almost
  certainly positively correlated, which would make the true uncertainty in `Lc − Le` smaller
  than this independence-based estimate — i.e., this project's `D` uncertainty is more likely
  to be an overestimate than an underestimate, which was a deliberate choice (better to
  overstate uncertainty on the weakest target than understate it).
- `D` is corroborated by this project's own prior finding (via the fully independent original
  ML pipeline) as the weakest-modeled of the three targets (GPR CV R² ≈0.665–0.713 vs.
  ≈0.977–0.994 for Lc/Le). The synthetic-data validation report (`05_VALIDATION_REPORT.md`)
  independently reproduces this same weakness a second way (largest correlation-structure
  shift, highest outlier rate of any output column). This convergence across two independent
  analyses is treated as evidence the limitation is real, not an artifact of one script.

## Assumptions specific to the input sampling

- `T1..T5` are sampled **continuously** within the observed per-column ranges from
  `original_train.csv`, not restricted to the 96 original discrete factorial levels. This was
  a deliberate choice to produce genuinely new design points rather than re-draws of the
  existing 96 — but it means the synthetic input marginal distributions do **not** statistically
  match the original (confirmed by the KS tests in `05_VALIDATION_REPORT.md`, which is
  expected and explained there, not a defect).
- The physical ordering constraint `T1 ≥ T2 ≥ T3 ≥ T4 ≥ T5` is enforced by rejection sampling
  on every generated row (0 violations by construction), matching the 96/96 compliance rate in
  the original data.
- Ranges are taken from `original_train.csv` only (n=67), not the full 96-row dataset — this
  is the leakage boundary: `original_val.csv` and `original_test.csv` are never read by the
  generator, so the sampled ranges are very slightly narrower than the true full-dataset range
  would suggest. This is a deliberate leakage-avoidance cost, not an oversight.

## Sample-size limitation (stated explicitly, per the "most important requirement")

n = 96 (67 after the leakage-safe train split) is a **small** dataset for any generative
method. This project selected GP-based generation specifically because GPs are one of the few
methods that remain statistically defensible at this scale (see `02_METHODOLOGY_SELECTION.md`
for why the other four candidate methods — statistical marginal sampling, copula/multivariate-
Gaussian, physics-informed, and conditional generative models — were rejected). Even so:

- The generator cannot establish, confirm, or refute any underlying physical law; it only
  reproduces the statistical response surface visible in 67–96 simulation points. No physical
  law is asserted anywhere in this project's synthetic-data deliverables.
- Increasing the number of synthetic rows generated (2000 in the delivered dataset) does
  **not** increase the amount of real information the generator has access to — it increases
  only how finely that same 67-point-derived response surface is sampled. This is why
  `04_generate_synthetic_data.py` defaults to a moderate multiple (~20x) of the original
  sample size rather than the 1000–5000 upper end suggested in the brief without
  justification: more synthetic rows would not make the underlying model more correct, only
  more densely sampled from the same (limited) fit.
- Any ML model trained on this synthetic data inherits every one of the above limitations. The
  ML evaluation (`06_ml_evaluation.py`, `06_MODEL_EVALUATION_REPORT.md`) evaluates strictly
  against real, untouched original test data specifically so that any performance claim about
  synthetic augmentation is checked against reality rather than against the synthetic
  generator's own (circular) output.

## What was explicitly NOT done

- No physical law, heat-transfer equation, or CrysMAS re-simulation was fabricated or assumed.
- No held-out test-set information was used to fit the generator or select its hyperparameters.
- No synthetic row was constructed by duplicating or lightly perturbing an original row (see
  the near-duplicate detection results in `05_VALIDATION_REPORT.md`: 0 near-duplicates found).
- No target variable was used as an input feature to another target's model.
- No claim is made, anywhere in this project's deliverables, that synthetic-augmented training
  improves model performance unless that specific claim is demonstrated on the untouched
  `original_test.csv` — see `06_MODEL_EVALUATION_REPORT.md` for whether that was or was not
  observed.
